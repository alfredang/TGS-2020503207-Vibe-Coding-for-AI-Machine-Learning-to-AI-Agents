## Goal

Use an AI coding agent to build a working application without hand-writing the implementation, following a disciplined loop rather than one-shot prompting. The specification you write is the real deliverable; the agent produces the code.

## What you'll build

A working research-assistant agent generated by a coding agent from your written specification, with an acceptance test you defined before any code existed.

**Tools:** Claude Code / Gemini CLI / Cursor, Python, Git

## Prerequisites

- Git installed and configured (`git --version`).

## Step-by-step

### 1. Install and launch your vibe coding tool in an empty project folder, then initialise Git

```bash
mkdir lab-03-research-agent && cd lab-03-research-agent
git init
claude
```

Git first, before any AI writes a line. Every change the agent makes then becomes a reviewable diff, and `git checkout .` is your undo button when a generation goes wrong. Without Git you have no way to see what changed or to roll it back.

### 2. Write SPEC.md first

This is the highest-value step in the lab. Write it yourself — do not ask the agent to write its own specification. Create `SPEC.md`:

```markdown
# SPEC — Research Assistant Agent

## Goal
A command-line agent that answers a research question by searching a local
document collection and citing which documents it used.

## Inputs
- `python research_agent.py "<question>"` — the question as one CLI argument.
- `documents/` — a folder of `.txt` files forming the searchable collection.

## Outputs
- A prose answer to stdout, under 200 words.
- A "Sources:" line listing the filenames actually used.
- Exit code 0 on success, 1 on any error.

## Constraints
- Python 3.11+, standard library plus `openai` and `python-dotenv` only.
- No web access — the agent may only read files under `documents/`.
- The API key is read from `OPENAI_API_KEY` via python-dotenv. Never hard-coded.
- The agent loop is capped at 5 turns.
- If no document is relevant, say so explicitly rather than inventing an answer.

## Acceptance test
Given `documents/mrt.txt` containing "The Thomson-East Coast Line opened in 2020":

    python research_agent.py "When did the Thomson-East Coast Line open?"

MUST print an answer containing "2020" and a "Sources:" line naming `mrt.txt`.

Given a question with no relevant document:

    python research_agent.py "What is the capital of Peru?"

MUST state that no relevant document was found, and MUST NOT answer "Lima".
```

Note what makes this specification useful: concrete file paths, an exact command, and a pass/fail test with a *negative* case. "Build me a research agent" gives the agent nothing to aim at.

### 3. Ask the agent to scaffold only the project structure and dependencies

Structure first, logic second. A prompt like this keeps the first generation small enough to actually review:

> Read SPEC.md. Create only the project skeleton: `research_agent.py` with function stubs and docstrings matching the spec, `requirements.txt`, a `documents/` folder containing the `mrt.txt` fixture from the acceptance test, and a `.gitignore` that excludes `.env` and `__pycache__`. Do not implement any function bodies yet — leave `raise NotImplementedError`.

Review what appears. If the structure is wrong, fixing it now costs one prompt; fixing it after the logic is written costs a rewrite.

```bash
git add -A && git commit -m "Scaffold research agent per SPEC.md"
```

### 4. Direct the agent to implement one component at a time

Ask for one function, review the diff, then ask for the next:

> Implement `search_documents(query)` only. It reads every `.txt` file under `documents/`, scores each by keyword overlap with the query, and returns the top 3 as a list of `{"filename": str, "content": str}`. Do not touch any other function.

Then:

> Now implement `run_agent(question)` — the loop from SPEC.md, capped at 5 turns, exposing `search_documents` as a function tool.

Review each diff with `git diff` before accepting. The reviewing is your job; the typing is the agent's. A 400-line single generation is not reviewable, which is why one component at a time is the rule.

### 5. Run the code and paste real error output back to the agent

```bash
pip install -r requirements.txt
python research_agent.py "When did the Thomson-East Coast Line open?"
```

When it fails — and the first run usually does — copy the whole traceback into the agent verbatim:

> Running the acceptance test gives this traceback:
>
> ```
> Traceback (most recent call last):
>   File "research_agent.py", line 62, in run_agent
>     messages.append({"role": "tool", "content": json.dumps(result)})
> openai.BadRequestError: Error code: 400 - messages with role 'tool' must
> have a 'tool_call_id'
> ```
>
> Fix this and explain what was wrong.

Concrete errors produce concrete fixes. "It doesn't work" produces guesses.

### 6. Verify against the acceptance test in SPEC.md, then commit the working state

Run **both** cases from the specification, including the negative one:

```bash
python research_agent.py "When did the Thomson-East Coast Line open?"
python research_agent.py "What is the capital of Peru?"
echo "exit code: $?"
```

The first must print 2020 and cite `mrt.txt`. The second must decline rather than answering "Lima" — an agent that passes the positive case and fails the negative one is a hallucinating agent, which is exactly what the negative case exists to catch.

```bash
git add -A && git commit -m 'Working research agent per SPEC.md'
```

### 7. Refine one improvement at a time, re-running the acceptance test after each change

Pick a single improvement, apply it, re-run both acceptance cases, commit. For example:

> Add a `--verbose` flag that prints which documents were retrieved and their scores before the answer. Do not change the default output format — the acceptance test must still pass.

Re-running the acceptance test after every change is what stops refinement from silently breaking what already worked. Batching five improvements into one prompt and then discovering a regression leaves you unable to tell which change caused it.

## Test it

Verify each of the following:

- [ ] `SPEC.md` was committed **before** any implementation code.
- [ ] The generated agent passes the positive acceptance case: the answer contains "2020" and cites `mrt.txt`.
- [ ] The generated agent passes the negative acceptance case: it declines to answer about Peru instead of inventing "Lima".
- [ ] `git log --oneline` shows several small commits (scaffold, per-component, fixes) rather than one giant unreviewed dump.
- [ ] `git show` on any commit produces a diff small enough to read in under a minute.
- [ ] No API key appears anywhere in the tracked source: `git grep -i "sk-"` returns nothing.

## What you learned

- The specification is the deliverable; writing `SPEC.md` before any code is what makes the agent's output verifiable.
- An acceptance test written in advance — including a negative case — is the difference between "it ran" and "it works".
- Scaffold before logic, and one component per generation, so every diff stays reviewable.
- Pasting real error output produces far better fixes than describing the symptom.
- Git is the control surface for AI-generated code: small commits, readable diffs, and a reliable undo.
